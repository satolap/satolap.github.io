Why teams use it

Manage users, groups, applications, service principals, entitlement management and Conditional Access the same way you manage the rest of your infrastructure: reviewed, versioned and repeatable.

Built from Microsoft's metadata

Generated modules come from the OpenAPI and EDMX definitions in msgraph-metadata. Every release pins the exact upstream commit and SHA-256 hashes.

Official provider underneath

Modules wrap the microsoft/msgraph provider's msgraph_resource, which supports Azure CLI, managed identity, service principal and OpenID Connect authentication.

Typed inputs, stable outputs

Each module has typed Terraform variables, request shaping that omits null optional properties, stable outputs and a README with the Graph URL, lifecycle and import address.

Tested before every release

Every module is formatted, initialised and validated against pinned provider versions. Credential-free terraform test suites use provider mocks.

Two collections, one release

Every release ships both collections under one version. They are subdirectories of the Registry module satolap/modules/msgraph.

Generated modules

These cover create, read, update and delete lifecycles from the v1.0 and beta schemas, for collection endpoints with a documented POST and an item lifecycle of GET, PATCH or PUT, and DELETE. A module's folder is its Graph route.

Browse the v1.0 catalog or the beta catalog. Both are grouped by Microsoft Graph service area.

Verified modules

These are reviewed, higher-level modules for common directory and governance scenarios, with documented permissions, lifecycle choices and relationship cleanup. Conditional Access policies default to report-only and require break-glass exclusions.

Quick start

Configure the Microsoft Graph provider in your root module, then reference a module by its directory after //, pinned to a release.

Module sources take three forms:

satolap/modules/msgraph//v1.0/<graph-route>
satolap/modules/msgraph//beta/<graph-route>
satolap/modules/msgraph//verified/<module-path>

Verified modules need Terraform 1.11 or later. On the 0.x line, ~> {{MINOR}}.0 takes fixes only. Read the migration notes before you move to a new minor version. The provider documents how to authenticate.

terraform {
  required_providers {
    msgraph = {
      source  = "microsoft/msgraph"
      version = ">= 0.3.0, < 0.7.0"
    }
  }
}

provider "msgraph" {}

module "engineering_group" {
  source  = "satolap/modules/msgraph//verified/groups"
  version = "~> {{MINOR}}.0"

  # Inputs use Microsoft Graph's property names.
  displayName     = "Engineering"
  mailNickname    = "engineering"
  securityEnabled = true
}

Release integrity you can audit

Every published catalog passes these automated checks before its release tag is created.

  1. Source manifests and cached metadata are checked against their recorded revisions and SHA-256 hashes.
  2. Python regression tests cover schema reconciliation, type generation, classification, deterministic output, safe archive handling and atomic publication.
  3. terraform fmt -check, terraform init -backend=false and terraform validate run for every generated and verified module, against the exact provider versions in the release manifest.
  4. Credential-free terraform test suites use provider mocks. They check Graph URL construction, typed request bodies, omission of null optional properties, validation failures and verified relationship behaviour, without contacting a tenant.
  5. The release workflow rebuilds the archives from the tagged commit and requires their byte-level SHA-256 checksums to match the tested artifacts. It then creates a build provenance attestation for every release asset.

A daily scheduled workflow rebuilds every published release and fails if a tag, an asset digest or an attestation no longer matches. Each release includes the v1.0, beta and verified archives, plus release-manifest.json, interface-changes.json and SHA256SUMS.

Mock tests and schema validation do not prove that a caller has the required Microsoft Graph permissions, licence or tenant configuration. Each module's README links to the API documentation for those requirements. Live-tenant integration checks are separate and opt-in.

FAQ

Which Terraform provider do the modules use?

The official microsoft/msgraph provider. The modules add typed inputs, request shaping, documentation and tests on top of its generic msgraph_resource.

Can I use beta modules in production?

Beta modules carry Microsoft's preview status: the underlying APIs can change without notice. Prefer v1.0 modules where they exist, pin versions, and read each release's interface changes before upgrading.

Does a first terraform init download everything?

Yes. Terraform downloads the whole catalog once for every module block, even though each block uses one directory. Pin a version so that download happens once.

Can I consume the modules from GitHub instead of the Registry?

Yes. Use a Git source pinned to a release tag, for example git::https://github.com/satolap/terraform-msgraph-modules.git//v1.0/<graph-route>?ref={{TAG}}.

Which permissions do I need?

Verified module READMEs document the permissions they need. Generated module READMEs link to Microsoft's API documentation, which lists the permissions for each operation. Grant only what the modules you use require.
