What it is

One Terraform Registry module, satolap/modules/msgraph, whose subdirectories are the modules. Generated modules cover the create, read, update and delete lifecycles of the Graph v1.0 and beta schemas. Verified modules are reviewed, higher-level modules for directory and governance scenarios. Both wrap the official provider's msgraph_resource; nothing is fetched from Microsoft during init, plan or apply.

Why teams use it

Manage users, groups, applications, service principals, entitlement management and Conditional Access the same way you manage the rest of your infrastructure: reviewed, versioned and repeatable.

Built from Microsoft's metadata

Generated modules come from the OpenAPI and EDMX definitions in msgraph-metadata. Every release pins the exact upstream commit and SHA-256 hashes.

Official provider underneath

Modules wrap the microsoft/msgraph provider's msgraph_resource, which supports Azure CLI, managed identity, service principal and OpenID Connect authentication.

Typed inputs, stable outputs

Each module has typed Terraform variables, request shaping that omits null optional properties, stable outputs and a README with the Graph URL, lifecycle and import address.

Tested before every release

Every module is formatted, initialised and validated against pinned provider versions. Credential-free terraform test suites use provider mocks.

Two collections, one release

Every release ships both collections under one version. They are subdirectories of the Registry module satolap/modules/msgraph.

Generated modules

These cover create, read, update and delete lifecycles from the v1.0 and beta schemas, for collection endpoints with a documented POST and an item lifecycle of GET, PATCH or PUT, and DELETE. A module's folder is its Graph route. Actions, functions and listing helpers are outside this subset.

Browse the v1.0 catalog or the beta catalog. Both are grouped by Microsoft Graph service area.

Verified modules

These are reviewed, higher-level modules for common directory and governance scenarios, with documented permissions, lifecycle choices and relationship cleanup. Conditional Access policies default to report-only and require break-glass exclusions.

Each module page states its assurance level: whether it was accepted in a live tenant run or validated offline only. Browse the catalog.

Get started

Three steps, taken from the release README. Verified modules need Terraform {{TF_MIN}} or later, and {{PROVIDER_LINE}}.

1. Configure the provider

The provider documents how to authenticate: Azure CLI, managed identity, service principal or OpenID Connect. Grant only the Graph permissions the modules you use require; each verified module's README lists them.

2. Reference a module, pinned to a release

Module sources take three forms. <module-path> is the path shown on a verified module's page; <graph-route> is a generated module's directory in its catalog.

satolap/modules/msgraph//v1.0/<graph-route>
satolap/modules/msgraph//beta/<graph-route>
satolap/modules/msgraph//verified/<module-path>

On the 0.x line, ~> {{MINOR}}.0 takes fixes only. Read the migration notes in the release before you move to a new minor version.

3. Initialise and plan

Terraform downloads the whole catalog once per module block on the first terraform init, so pin a version and that download happens once. Review the plan before you apply.

terraform {
  required_providers {
    msgraph = {
      source  = "microsoft/msgraph"
      version = ">= 0.4.0, < 1.0.0"
    }
  }
}

provider "msgraph" {}

module "engineering_group" {
  source  = "satolap/modules/msgraph//verified/groups"
  version = "~> {{MINOR}}.0"

  # Inputs use Microsoft Graph's property names.
  displayName     = "Engineering"
  mailNickname    = "engineering"
  securityEnabled = true
}

From GitHub instead of the Registry

A Git source pins the same release by its tag:

git::https://github.com/satolap/terraform-msgraph-modules.git//v1.0/<graph-route>?ref={{TAG}}

Release integrity you can audit

Every published catalog passes these automated checks before its release tag is created.

  1. Source manifests and cached metadata are checked against their recorded revisions and SHA-256 hashes.
  2. Python regression tests cover schema reconciliation, type generation, classification, deterministic output, safe archive handling and atomic publication.
  3. terraform fmt -check, terraform init -backend=false and terraform validate run for every generated and verified module, against the exact provider versions in the release manifest.
  4. Credential-free terraform test suites use provider mocks. They check Graph URL construction, typed request bodies, omission of null optional properties, validation failures and verified relationship behaviour, without contacting a tenant.
  5. The release workflow rebuilds the archives from the tagged commit and requires their byte-level SHA-256 checksums to match the tested artifacts. It then creates a build provenance attestation for every release asset.

A daily scheduled workflow rebuilds every published release and fails if a tag, an asset digest or an attestation no longer matches. release-manifest.json records the upstream metadata commit, provider versions, dependency hashes and the complete input fingerprint, so the inputs of any release can be audited.

Mock tests and schema validation do not prove that a caller has the required Microsoft Graph permissions, licence or tenant configuration. Each module's README links to the API documentation for those requirements. Live-tenant integration checks are separate and opt-in; a verified module's page states whether it has one.

What to pin

Pin a patch-only constraint such as ~> {{MINOR}}.0 to take fixes only. Before a new minor version, read the release's breaking changes and migration notes; blocking changes are published only when a reviewed release decision accepts them.

Beta modules

Microsoft Graph beta APIs are previews and can change incompatibly; Microsoft recommends v1.0 for production. See Microsoft's versioning and support policy.

Support and policies

Support runs in the open, on GitHub. The public repository publishes these channels and commitments.

Problems and module requests

Open a GitHub issue with the release tag and module path, your Terraform and provider versions, a minimal configuration, the expected and actual result, and sanitised logs. Templates exist for bug reports, module requests and accessibility barriers.

Security

Report a suspected vulnerability privately through GitHub's vulnerability reporting, never in a public issue. Expect an initial acknowledgement within seven days. Fixes are applied to the latest release and main; older tags are immutable, so upgrade after a fix is published. Read the security policy.

Provider and Graph issues

Problems in the microsoft/msgraph provider or in the Microsoft Graph API itself belong upstream, in the provider's issue tracker.

Changing a module

The module trees are published from a validated pipeline, so pull requests that edit them cannot be accepted: open an issue describing the change instead. Pull requests are welcome for the public documentation and release tooling. See CONTRIBUTING.md.

Licensing

The code and verified modules are available under the MIT License. Generated interfaces derive from Microsoft Graph metadata (MIT) and documentation (CC BY 4.0); NOTICE lists the upstream notices.

Accessibility

FAQ

Which Terraform provider do the modules use?

The official microsoft/msgraph provider. The modules add typed inputs, request shaping, documentation and tests on top of its generic msgraph_resource.

Which Terraform version do I need?

Every verified module requires Terraform {{TF_MIN}} or later, and {{PROVIDER_LINE}}. The Requirements section on each module page states its own Terraform and provider constraints.

Can I use beta modules in production?

Beta modules carry Microsoft's preview status: the underlying APIs can change without notice. Prefer v1.0 modules where they exist, pin versions, and read each release's interface changes before upgrading.

Does a first terraform init download everything?

Yes. Terraform downloads the whole catalog once for every module block, even though each block uses one directory. Pin a version so that download happens once.

Can I consume the modules from GitHub instead of the Registry?

Yes. Use a Git source pinned to a release tag, for example git::https://github.com/satolap/terraform-msgraph-modules.git//v1.0/<graph-route>?ref={{TAG}}.

Which permissions do I need?

Verified module READMEs document the permissions they need. Generated module READMEs link to Microsoft's API documentation, which lists the permissions for each operation. Grant only what the modules you use require.

What does "verified live-accepted" mean on a module page?

The module's README records a live tenant run that was accepted on the stated date and commit. "verified offline-only" means the module passed the offline checks (validation and mock tests) and has no recorded live run. The README's Assurance line is the source.

Is there a support commitment?

Support is public and community-based: GitHub issues for problems and module requests, and private vulnerability reporting with an acknowledgement within seven days. The repository states no other support commitment.
